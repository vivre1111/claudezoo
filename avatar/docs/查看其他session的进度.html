查看本机其他 Claude Code session 的进度

这份文档的读者是另一个 Claude Code session——尤其是从同一个会话 fork 出来、 正在并行推进同一个项目的兄弟 session。你需要知道：对方现在做到哪一步了？它是在等人类、 在跑工具，还是卡住了？它的待办清单还剩什么？ 全文所有结构、字段和数字都来自 2026-08-22 对本机 ~/.claude 的实际扫描， 以及 D:\avatar\zoo_server.py（1083 行，已在本机长期运行验证）里跑通的读法。

先说红线：全程只读。 本文所有做法都只读取文件、只做只读的进程查询。不要写入 ~/.claude 下的任何文件—— 那是别人正在追加写的活文件；不要试图用信号或 API 去干预别的 session 的进程；不要把 读到的内容发到任何外部服务。你是在旁观，不是在操控。 Windows 上尤其注意：os.kill(pid, 0) 在 POSIX 上是无害探活，在 Windows 上 Python 会把它翻译成 TerminateProcess，真的会把那个 session 杀掉。

1. 三条路：读文件、直接喊话、看工作区

1.1 要解决什么

两个 fork 出来的 session 各自在推进同一个项目的不同分支（比如一个搭原型、一个写实现）， 但它们互相看不见。人类在两个窗口之间来回切换，很容易出现：A 已经改了数据库 schema， B 还在按旧 schema 写代码；或者两边同时在做同一件事。 你需要一个办法，在不打扰对方、不等人类转述的前提下知道对方的状态。

1.2 怎么做

有三条完全不同的路，代价和实时性都不一样，按需要挑：

路子看到什么代价什么时候用
A. 读 ~/.claude 文件对方的完整转录、待办、状态 只读几个文件，毫秒级，对方无感默认选它。想知道"它到底做了什么"
B. 直接喊话
ListAgents / SendMessage		 对方主动回答你的问题会打断对方、消耗它的 token需要对方决策或确认时
C. 看共享工作区
git log / docs/		 对方已经落地的产出几乎为零只关心"结果有没有出来"

路 A 是本文的主线，第 2–5 节都在讲它。 路 B 值得单独说一句：ListAgents 在本机实测可用，返回的是同机的对等 session：

Peer sessions (4):
  claude-1a [67760d]  ·  interactive  ·  started 1h ago
  vivre-c2 [e5adce]  ·  interactive  ·  started 0s ago
  claude-f3 [36de93]  ·  interactive  ·  started 6m ago
  claude-fc [164e36]  ·  interactive  ·  started 1h ago

那个 claude-1a 就是注册表文件里的 name 字段，也是 SendMessage 的收件地址。底层传输是注册表里的 messagingSocketPath，在 Windows 上是一条命名管道， 形如 \\.\pipe\cc-msg-403563cb5dbf0a5fbdc8263623ecb84d。

为什么默认选"读文件"而不是"直接问"： 喊话看着更直接，但它有三个隐性代价。 其一，会打断对方——消息会进到对方的输入队列，它得停下手里的活来读、来回； 如果两个 session 互相喊，很容易变成两边都在回消息、都没在干活。 其二，你拿到的是转述，不是事实——对方会用自己的话总结进度， 而转录文件里是它实际调用了什么工具、改了哪个文件，后者才是可对账的。 其三，不是所有 session 都能喊：本机 48 条注册表条目里只有 11 条带 messagingSocketPath，因为这是较新版本才有的能力（实测 2.1.235 / 2.1.237 全部有， 2.1.229 及更早全部没有，2.1.234 处在过渡期——9 条里只有 1 条有）。老版本的 session 你喊不动， 但它的文件照样读得到。

所以顺序应该是：先读文件把事实搞清楚，确实需要对方做决定时才喊话。
它骗你的地方：ListAgents 只列出还活着的对等 session。 一个刚被关掉的 fork，喊不到，但它的转录文件完整保留在磁盘上—— "喊不到"绝不等于"没这个 session"，更不等于"它没干过活"。 反过来，路 C（看 git）只能看到已提交的东西，对方改了但没提交的工作区内容你看不见。

2. 数据在哪儿：~/.claude 的四个仓

2.1 要解决什么

"session 的状态"不是存在一个地方的。它被拆在四个目录里，各存一部分， 而且关联它们的键不止一个。不知道这个布局，就只能靠猜文件名。

2.2 怎么做

① 注册表 ~/.claude/sessions/<pid>.json

每个活着的 session 一条。本机现有 48 条 .json（另有若干 .key 文件，无视即可）。 实测出现过的全部字段：

<slug> 是 cwd 把非字母数字全换成 - 得到的，比如 D:\avatar → D--avatar。注意中文路径会被压成一串连字符 （C--Users-vivre-Desktop-workspace-------），所以别想着从 slug 反推路径—— 要拿路径就读注册表的 cwd。找转录文件直接用 sessionId 全目录 glob 最省事：

glob.glob(os.path.join(PROJECTS_DIR, "*", session_id + ".jsonl"))

        if e.get("type") in ("user", "assistant")

④ 小弟 ~/.claude/projects/<slug>/<sid>/subagents/

注意这个目录跟转录文件同名并列：<sid>.jsonl 是文件，<sid>/ 是目录。 里面每个后台 agent 两个文件：agent-<id>.jsonl（它自己的完整转录，实测最大 527 KB / 91 行） 和 agent-<id>.meta.json：

{
  "agentType": "general-purpose",
  "description": "Security review of backup app",
  "toolUseId": "toolu_01Y4TyDHsoqCV7v94wDvAita",   // ← 指回主转录里那次调用
  "spawnDepth": 1,
  "model": "opus"
}

本机共 16 个 meta 文件。toolUseId 是把小弟接回主线的钥匙。

为什么 ClaudeZoo 不用 meta 文件判断"小弟还在不在跑"： 最直觉的做法是数一数 subagents/ 下有几个 meta——但那是历史全集， 跑完的也留在那儿，数出来永远只多不少。实测早期版本就栽在这：一个 49 MB 的转录报出 "4 个还在跑"，其实结果早回来了。正确的判据在转录里，见 4.4。

3. 找到"兄弟"：为什么不能靠 sessionId

3.1 要解决什么

你是一个 fork，你想找到"跟我同源的另外几个 session"。 最自然的想法是找一个 parent 字段顺藤摸瓜。没有这个字段。 更糟的是，sessionId 本身就不稳定——同一条工作线，关掉再打开就换一个 id。

3.2 怎么做：先看血缘的真实痕迹

fork 的时候，Claude Code 会把父会话的历史整段复制进新文件， 而复制进来的那些行仍然带着父会话的 sessionId。 于是出现一个可检测的特征：文件名 ≠ 文件里记录的 sessionId。

本机 72 个转录文件里，有 3 个存在这种不一致。逐行扫描其中一个：

2b3a3958-….jsonl   共 4431 行  10.9 MB
    7f8c432c   2903 条  首次出现在行 0      ← 继承来的历史
    2b3a3958   1528 条  首次出现在行 2903   ← 自己的记录从这儿开始

切换点非常干净：行 0–2902 全是父会话 7f8c432c 的，行 2903 起换成自己的。 这就是fork 点。同一个父会话还派生出另外两个：

文件总行数继承自继承了多少行标题
7f8c432c2921——开发电机在线监测算法库和模块原型
119e76fa18727f8c432c1866淮北矿业电机在线监测
20ae1d9029257f8c432c2903淮北矿业电机在线监测 (fork prototype)
2b3a395844317f8c432c2903淮北矿业电机在线监测 (fork implement)

继承行数还告诉你在父会话的哪一刻分的叉：1866 行那次分得早，2903 行那两次分得晚 （而且是同一个点分出去的两条）。

但这个办法会漏。实测当下活着的三个"电机在线监测" session： 
2b3a3958   4431 行 = 2903 继承 + 1528 自己   ← 血缘可见 ✔
579c0c4b   1016 行，全部是自己的               ← 标题写着 (fork prototype)，但查不出血缘 ✘
c6b3b52c    993 行，全部是自己的               ← 名字像"父会话"，其实也不是 7f8c432c
579c0c4b 明明是 20ae1d90 那条 prototype 线的延续（标题一模一样）， 但它的转录里一行继承历史都没有。原因是：fork 出来的会话关掉再恢复时， 新会话拿到新的 sessionId、开一个全新的转录文件，不再复制历史——血缘线索到此为止。

所以："文件名≠内部 id" 只能识别 fork 后还没重启过的那一代。 它是一条有用的线索，不是可靠的族谱。

3.3 为什么选它：真正稳定的身份是 cwd + 标题

sessionId 每次重启都换，不能当作"这条工作线"的身份。 实测那 4 个 id 全都指向同一条工作线，人类眼里它就是"电机在线监测"这一个项目。 真正跨重启保持稳定的是两样东西：
  • cwd——注册表里的工作目录。上面三个活着的 session，cwd 完全相同。
  • custom-title——人类起的标题，重启后会带过来，而且 fork 通常在后面加后缀： … (fork prototype) / … (fork implement)。
找兄弟的正确姿势：按 cwd 分组，再看标题的公共前缀。 血缘扫描留着当补充证据用（它能告诉你分叉点在哪），但不要拿它当主判据。

4. 判断"它现在干到哪一步"

4.1 要解决什么

拿到转录之后，你要回答一个很具体的问题：球现在在谁手上？ 是它在算、在等工具、在等人类，还是在等自己派出去的小弟？ 判错的后果很实际：以为它在等人类，跑去催人类；其实它正跑得欢。

4.2 怎么做：stop_reason 才是权威信号

直觉做法是看最后一条 assistant 记录里有没有 tool_use 块： 有就是在干活，没有就是说完了。这是错的。

一个回合会被拆成好几条记录。 思考 → 文字 → 工具调用，这三条各自是一条独立的 assistant 记录， 而且三条的 stop_reason 都是 tool_use。 你轮询的时刻要是正好落在中间那条（只有文字、没有 tool_use 块）， "有没有 tool_use 块"这个判据就会把一个干得正欢的 session 判成"等你回话"。 正确的判据是 message.stop_reason：
stop_reason含义
end_turn整轮真的答完了，球在人类那边
tool_use话说到一半，马上要动手

把 stop_reason、最后一条记录的形状、静置时长三者合起来， 就是 zoo_server.py 里 classify() 的判定表 （DOZE_AFTER = 300 秒是"打盹"门槛）：

最后一条记录附加条件判定球在谁手上
assistant含 tool_use 块，静置 < 300s正在用某工具它自己
含 tool_use 块，静置 > 300s卡住了可能需要人类
end_turn 且有在跑的小弟等后台 agent小弟
end_turn，无小弟答完了 / 打盹人类
非 end_turn 且静置 > 300s半路停下（被 Esc 或断了）人类
user含 tool_result 块在消化工具结果它自己
user不含在读新指令它自己

4.3 还有两个高价值信号

人类最后说的那句话——用 last-prompt 记录，不要从 user 消息里翻：

{"type": "last-prompt",
 "lastPrompt": "扩充下片单，它12个弄完又循环到1了",
 "leafUuid": "b78cacaf-…", "sessionId": "22b7e08b-…"}
为什么不从 user 消息里翻：user 类型的记录里混着 工具结果回填、图片附件、/skill 展开后的一大段模板——它们都长得像"人类说的话"， 但都不是。last-prompt 是 Claude Code 专门记的一行，直接就是人类打进去的原文。

排队等它处理的输入——queue-operation，这是"对方接下来要做什么"的直接证据：

{"type": "queue-operation", "operation": "enqueue",
 "timestamp": "2026-08-22T03:39:24.538Z", "sessionId": "22b7e08b-…",
 "content": "再doc里生成下查 session info的方式…"}

4.4 在跑的后台小弟：靠通知配对，不靠工具结果

后台 Agent 是发射后即返回的：tool_result 立刻回一句 Async agent launched successfully。所以拿 tool_use ↔ tool_result 配对永远配得上，判断不出跑没跑完。真正的完工信号是后面单独追加的一条 <task-notification>（一条纯文本 user 消息），里面的 <tool-use-id> 指回当初那次调用。所以配对的两头是：

tool_use.id   ←→   <task-notification> 里的 <tool-use-id>
两个真实踩过的坑，抄这段代码时必须一起抄：
  1. 只扫尾部窗口，两头都要在窗口内。如果某个老会话的"发射"和"通知"都被甩出了尾部窗口， 你两头都看不见，于是不会误报它"还在跑"。这是刻意的：宁可漏报也不误报。
  2. 先确认这条结果属于 Agent 调用（tool_use_id in desc），再看内容。 否则任何工具的输出只要正文里恰好出现 "Async agent launched" 这句话，就会被当成派出去一个小弟—— 实测把这句打印到终端做排查，就足以让自己那张卡凭空多出两个小弟。

5.2 完整代码

纯标准库，无依赖。核心部分：

import ctypes, glob, json, os, re, sys, time
from ctypes import wintypes

HOME     = os.path.expanduser("~")
SESSIONS = os.path.join(HOME, ".claude", "sessions")
PROJECTS = os.path.join(HOME, ".claude", "projects")
TASKS    = os.path.join(HOME, ".claude", "tasks")
TAIL     = 300_000

# ---- 探活：Windows 上绝不能用 os.kill(pid, 0)，那是 TerminateProcess，真会杀人 ----
if sys.platform == "win32":
    _k32 = ctypes.WinDLL("kernel32", use_last_error=True)

    def alive(pid):
        h = _k32.OpenProcess(0x1000, False, pid)   # QUERY_LIMITED_INFORMATION
        if not h:
            return False
        try:
            code = wintypes.DWORD()
            ok = _k32.GetExitCodeProcess(h, ctypes.byref(code))
            return bool(ok) and code.value == 259  # STILL_ACTIVE
        finally:
            _k32.CloseHandle(h)
else:
    def alive(pid):
        try:
            os.kill(pid, 0)                        # POSIX 上 signal 0 才是真探活
            return True
        except OSError:
            return False


def tail_entries(path, limit=TAIL):
    """只读文件尾部一段。转录能到 22 MB，整读既慢又没必要。"""
    size = os.path.getsize(path)
    with open(path, "rb") as f:
        if size > limit:
            f.seek(size - limit)
            f.readline()                           # 这行大概率是半截的，扔掉
        raw = f.read()
    out = []
    for line in raw.decode("utf-8", "ignore").splitlines():
        line = line.strip()
        if line.startswith("{"):
            try:
                out.append(json.loads(line))
            except ValueError:
                pass
    return out


def load_live():
    """活着的 session。注意注册表是按 pid 命名的，同一个 session 会有好几条。"""
    out = []
    for p in sorted(glob.glob(os.path.join(SESSIONS, "*.json"))):
        try:
            meta = json.load(open(p, encoding="utf-8"))
        except (OSError, ValueError):
            continue
        pid = meta.get("pid")
        if pid and not alive(int(pid)):
            continue                               # pid 没了 = 幽灵条目
        if meta.get("sessionId"):
            out.append(meta)
    # 按 sessionId 去重，留 startedAt 最新的那条
    best = {}
    for m in out:
        k = m["sessionId"]
        if k not in best or (m.get("startedAt") or 0) > (best[k].get("startedAt") or 0):
            best[k] = m
    return list(best.values())


def agents_running(entries):
    """派出去还没回来的后台 agent。两头是 tool_use.id ←→ 通知里的 <tool-use-id>。"""
    desc, launched, finished = {}, set(), set()
    for e in entries:
        c = (e.get("message") or {}).get("content")
        text = c if isinstance(c, str) else ""
        if isinstance(c, list):
            text = " ".join(b.get("text", "") for b in c
                            if isinstance(b, dict) and b.get("type") == "text")
        if "<task-notification>" in text:
            finished.update(re.findall(r"<tool-use-id>(.*?)</tool-use-id>", text))
        if not isinstance(c, list):
            continue
        for b in c:
            if not isinstance(b, dict):
                continue
            if b.get("type") == "tool_use" and b.get("name") in ("Agent", "Task"):
                desc[b.get("id")] = ((b.get("input") or {}).get("description") or "后台任务")[:60]
            elif b.get("type") == "tool_result" and b.get("tool_use_id") in desc:
                # 必须先确认这条结果对应的调用【本身就是 Agent 工具】，再看内容，
                # 否则任何提到 "Async agent launched" 的输出都会被误判成派出了小弟
                body = b.get("content")
                if isinstance(body, list):
                    body = " ".join(x.get("text", "") for x in body if isinstance(x, dict))
                if isinstance(body, str) and "Async agent launched" in body:
                    launched.add(b.get("tool_use_id"))
    return [desc.get(i, "后台任务") for i in launched if i not in finished]

def lineage(sid, path):
    """文件里记录的 sessionId 跟文件名不一致的那段 = 继承来的历史。
    只对「fork 后还没重启过」的那一代有效，见文档第 3 节。"""
    parent, inherited = None, 0
    with open(path, encoding="utf-8", errors="ignore") as f:
        for line in f:
            line = line.strip()
            if not line.startswith("{"):
                continue
            try:
                s = json.loads(line).get("sessionId")
            except ValueError:
                continue
            if s and s != sid:
                parent, inherited = s, inherited + 1
            elif s == sid:
                break
    return parent, inherited

6. 六个会骗你的地方

① 注册表是按 pid 存的，不是按 session。 文件名是 <pid>.json。同一个 session 每次重启/恢复都会多出一条， 老条目要等那个 pid 真的死掉才消失。实测 7f8c432c 一个 sessionId 占了 5 条注册表条目，2b3a3958 和 579c0c4b 各占 2 条。 不去重的话，同一个 session 会被你数成好几个。（这正是 ClaudeZoo 早期"为什么有两个知识库"的原因。） 去重方法：先按 pid 过滤掉死的，再按 sessionId 取 startedAt 最新的一条。 本机实测 48 条 → 去重后 4 个活着的 session。
② 文件 mtime 会骗人。 转录文件经常被 mode / ai-title 这类记账记录碰新， mtime 于是很新——但那个 session 可能已经 14 天没说过话了。 "多久没动静"必须按最后一条真实消息的 timestamp 算，不能用 os.path.getmtime。
③ 尾部窗口会截断证据。 只读尾部 300 KB 是为了性能（本机最大的转录 22.1 MB，全读一次代价太大）。 代价是：发生在更早的事你看不见。这对"在跑的小弟"是安全的——两头都看不见就不会误报； 但对"这个 session 一共做了什么"是不安全的——你只看到了最近一小段。 要完整历史就得整文件扫，那时请做好几秒钟的心理准备。
④ 待办清单覆盖率很低。 tasks/ 只有用过 TodoWrite 的 session 才有。 实测本机 48 条注册表条目对应只有 7 个 session 有清单目录，而且其中只有 2 个还活着。 "没有清单"≠"没有进度"，只是它没用这个工具。别把空清单当成对方没干活。
⑤ cwd 可能已经变了。 转录里有 relocated 记录（本机抽样到 13 条），表示这个 session 的工作目录被改过。 注册表里的 cwd 是启动时的值。按 cwd 找兄弟时， 如果有人中途 relocate 过，分组就会错。
⑥ 你读到的永远是"刚才"，不是"现在"。 转录是异步落盘的，对方正在生成的那段文字还没写进文件。 一个显示"正在用 Bash"的 session，此刻可能已经跑完三个工具了。 不要基于转录去做需要强实时性的判断（比如"我等它写完这个文件再动手"）—— 真要同步，用第 1 节的路 B 喊话，或者约定用工作区里的文件/锁做握手。
